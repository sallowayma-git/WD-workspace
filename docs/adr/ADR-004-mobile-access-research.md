# ADR-004：手机端布置任务的同步方案调研（待决策）

- 状态：调研完成，暂不实施
- 日期：2026-09-19
- 关联：`ADR-002-local-desktop-runtime.md`

## 背景

当前产品的数据真值只存在电脑上的 SQLite 中，没有同步服务。手机端要能
布置任务，首先必须决定电脑与手机如何共享这份数据。本 ADR 只记录方案
边界与待确认问题，不引入网络服务、账号系统或移动端代码。

## 备选方案

### A. 局域网网页

桌面端启动一个仅监听局域网的 HTTP 服务，手机在同一 Wi-Fi 下通过浏览器
访问。SQLite 仍在电脑上，桌面端负责 API 与写入。

优点是无需上架应用商店，也不必迁移现有数据；实现范围主要是 HTTP API、
局域网发现/地址展示、短期访问凭证和鉴权。代价是电脑必须开机并与手机在
同一网络，离开局域网就不可用，还要认真处理恶意同网设备、凭证轮换、
跨域与服务生命周期。

### B. 轻量云同步

在本地 SQLite 之外记录变更日志，把变更同步到 Supabase 或自建服务；手机
与电脑各自持有本地副本，通过账号认证访问云端。

优点是电脑无需常开，手机可在外网使用，也为多个设备打下基础。代价是这
会改变“纯本地”产品边界，必须处理账号与权限、端到端数据保护、离线队列、
冲突合并（尤其是任务状态/排期/顺延链）、迁移与云服务运维成本。

### C. Tauri 移动端

用 Tauri 2 打包 iOS/Android 客户端。它只是客户端形态选择，不能替代同步
机制，因此仍然需要 A（移动端连接电脑）或 B（移动端连接云端）作为数据
通道。

优点是可以复用较多现有前端代码；代价是在 A/B 之外增加移动端适配、签名
与发布流程。iOS 需要开发者账号并通过 App Store 审核，或使用 TestFlight/
企业分发；Android 也需要签名、渠道和设备兼容性维护。

## 结论

本期不选择 A、B 或 C，也不开发手机端。客户明确以下两个问题后再做决策：

1. **电脑是否常开？** 若电脑通常常开且手机只在同一 Wi-Fi 使用，A 的前提
   成立；否则应优先评估 B。
2. **是否接受数据上云？** 若不接受，只能在 A 的纯本地边界内继续；若接受，
   B 才可作为长期方案，C 再作为客户端形态评估。

在答案明确前，继续保持 ADR-002 的纯本地边界；不得为了“预留手机端”而
偷渡云账号、HTTP 监听、变更日志或移动端工程。

## 决策检查表

| 客户答案          | 倾向方案                   | 下一步                                    |
| ----------------- | -------------------------- | ----------------------------------------- |
| 常开 + 不上云     | A                          | 设计局域网鉴权、服务发现、写入 API 与审计 |
| 不常开 + 接受上云 | B，再评估 C                | 设计变更日志、冲突策略、账号与云端运维    |
| 常开 + 接受上云   | A 做短期验证，B 做长期评估 | 先确认离线/外网需求再选                   |
| 不常开 + 不上云   | 当前目标不可满足           | 需要重新讨论可接受的设备/网络边界         |
